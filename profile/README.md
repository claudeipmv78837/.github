<p>成员离职是一次小型的环境变更，麻烦在于它同时牵动三样东西：谁能登录、哪条出口归谁、历史记录还查不查得到。处理得粗糙，常见后果是账号被遗留在某个没人管的出口上，或者反过来，为了「保险」把整组出口全换掉，连带把其他同事的登录环境也打乱。下面给一份按时间点排的清单，每一项都写明判断条件，能做到「该收的收干净，不该动的别动」。</p>

<h2>一、三件事必须先定：留痕、回收、换线</h2>
<p>离职处理的顺序不能颠倒。先把记录固定下来，再动权限，最后才谈出口。顺序反了会丢证据——权限一收，你连他最后一次用哪条线都不好查。</p>

<h3>先留痕：日志导出到自己的地方</h3>
<p>把他名下子账号最近 30 天的连接日志导出来，存到团队自己的存储里。重点看三列：出口 IP、目标域名、字节数。异常大的单日流量往往对应批量任务，这类记录后面可能用得上。供应商后台的日志保留期通常只有 7 到 30 天，过了就没了。</p>

<h3>再回收：按依赖顺序停用</h3>
<p>顺序是：业务系统账号、代理子账号、浏览器环境、二次验证绑定。代理子账号要在业务账号之后停，否则排查时会出现「登不进系统也查不到网络记录」的死角。二次验证的解绑放在最后，并且由接手人现场确认新设备能收到验证。</p>

<h3>最后谈线：出口是资源不是私人物品</h3>
<p>出口绑的是账号，不是人。他离职不代表这条线要作废，除非这条线只服务他一个人且账号本身也要停用。判断标准在第四节展开，先说结论：多数情况下不必换线，换的是凭据。</p>

<h2>二、T-3 天：把「他手上有什么」列成清单</h2>
<p>提前三天做盘点，比当天临时找要靠谱。盘点不是问「你还有什么没交」，而是拿系统里的记录反查：哪些子账号最近 90 天有活动、哪些出口绑在他名下、哪些设备登记过。</p>
<img src="/tp.png" alt="成员权限盘点表列出子账号、绑定出口与最近活动时间">
<p>反查的好处是不会漏。人对自己的使用习惯记不全，系统记录不会撒谎。把「最近 90 天有活动」作为筛选条件，能过滤掉早已废弃的子账号，避免把精力花在僵尸凭据上。</p>

<h3>三类要特别留意的资源</h3>
<p>一是长期不换的静态出口，这类资源通常绑定了重要账号，交接时必须逐个确认归属；二是共享给多人的白名单条目，删之前要确认没有别人的地址在同一行；三是存在本地未提交的配置，比如自定义的代理规则、脚本里的环境变量。</p>

<h3>盘点结果要对方签字</h3>
<p>清单打印或导出后由交接双方确认，写明「以上为全部资源」。这不是形式主义，后面如果冒出第五个没人知道的子账号，至少能定位是盘点漏了还是有人新建。</p>

<h2>三、T 日：冻结与回收的十二项核对</h2>
<p>当天按清单逐项打勾，不要凭记忆跳步。十二项听起来多，熟练后半小时能走完一遍，比事后补救便宜得多。</p>

<h3>账号侧六项</h3>
<p>业务登录、代理子账号、邮箱或通知渠道、二次验证、API 令牌、共享文档权限。API 令牌最容易被漏，尤其是脚本里硬编码的那种，停用后要顺手把仓库里的明文换掉。</p>

<h3>环境侧六项</h3>
<p>办公设备回收、浏览器配置文件归档、本地代理客户端卸载、路由器或软路由上的凭据、手机端代理配置、门禁与工位。环境侧不属于网络范畴，但漏一项就可能留下一个能登录的入口。</p>

<h3>异常情况的处理</h3>
<p>如果当天联系不上人、拿不到设备，优先做两件事：停代理子账号、吊销 API 令牌。设备可以后补，凭据不能等。反过来，如果设备已交回但人还在配合交接，可以先保留只读权限三到五天，降低沟通成本。</p>

<h2>四、出口要不要换：按三个条件判断</h2>
<p>换线是有代价的：新线要重新磨合，账号可能重新触发一次验证。所以只在满足条件时换，不为「心里踏实」而换。</p>

<h3>条件一：出口只服务这一个账号</h3>
<p>这条线如果从头到尾只挂他一个人的号，且这个号也要停用或迁移，那这条线可以回收或退订。反之，一条线上还挂着别人的号，就不该因为一个人离职而整体更换。</p>

<h3>条件二：凭据外泄风险无法确认</h3>
<p>如果交接时发现密码曾以明文形式存在聊天记录、文档或代码仓库里，且无法确认传播范围，那就把这条线的认证凭据重置，必要时换 IP。重置凭据的成本远低于换线。</p>

<h3>条件三：历史行为存在异常</h3>
<p>日志里出现非常规时段的大量请求、陌生目标域名，或者出口被第三方标记的记录，这类情况下换线更稳妥，同时把该账号单独隔离观察一段时间。</p>

<h2>五、T+7 天：复核与归档</h2>
<p>一周后做一次复核，重点看两件事：有没有凭据在被停用后又被使用，接手人的环境是否稳定。前者说明还有副本没清掉，后者说明交接是否真的完成。</p>

<h3>复核看三个信号</h3>
<p>网关日志里该子账号零记录、业务系统无异常登录告警、接手人一周内没有因为环境问题找你。三条都过，这次交接可以关闭。</p>

<p>归档要留四样东西：盘点清单、日志导出路径、停用时间点、出口处理结论，放在同一个目录里。半年后如果有人问「去年那条线为什么换的」，翻一次就能答上，不用重新推演。</p>

<h2>常见问答</h2>
<h3>离职当天就必须把出口换掉吗？</h3>
<p>答：不必。出口绑的是账号资源，先重置认证凭据通常已经足够；只有确认凭据外泄或存在异常行为时，换 IP 才有必要。盲目换线会让同一条线上的其他账号重新经历一次磨合。</p>

<h3>子账号停用后，他的历史记录还能查吗？</h3>
<p>答：取决于你是否提前导出。供应商后台一般按时间保留，与账号是否停用无关，但超过保留期就查不到。建议在停用前把最近 30 天日志导到自建存储，保留 90 天以上。</p>

<h3>交接期间要不要给他保留只读权限？</h3>
<p>答：如果确有在办事项且双方配合，可以保留三到五天的只读权限，同时把出口访问权限单独收回。关键是把「能看」和「能连」分开，不要一并放开。</p>

<h3>多人共用的出口，一个人离职会影响别人吗？</h3>
<p>答：正常情况下不影响，因为停用的是子账号凭据而不是出口本身。真正会影响别人的操作是改出口密码或换 IP，这两件事要提前通知同组的其他使用者并约定时间窗。</p>

<h2>合规提示</h2>
<p>离职处理涉及个人信息与操作记录，采集和使用应限于内部管理必要范围，并按个人信息保护相关法律要求告知与保存。不得将记录用于与人事管理无关的用途。</p>
<p>账号与网络资源属于企业资产，交接应通过正式流程完成并留档。任何情况下不应擅自使用他人账号或凭据访问系统。</p>
<p>本文流程为通用参考，具体停用顺序与保留期限应结合你所在组织的制度与合同约定调整。</p>
